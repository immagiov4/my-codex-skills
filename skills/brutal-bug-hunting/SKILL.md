# Brutal Bug Hunting

Use for a requested **systemic, cross-codebase bug hunt**, not a routine fix or ordinary code review. The deliverable is a defensible map of verified problems and remaining coverage, not a list of grep hits or an assertion that every bug was found. Follow the project's instructions and reuse existing debugging and issue-governance workflows.

## Contract and boundaries

- Establish the repository, revision, production/artifact relationship, relevant paths, user-requested depth, and allowed side effects. Preserve dirty worktrees and costly user input. Inspect production or backups only within the request; use isolated mocks for destructive or fault-injection tests. A production read, local reproduction, issue publication, and code fix are separate permissions.
- For model classification, obtain explicit authorization for the provider, data scope and spending before uploading source or issue content. Use the exact requested model, not a similarly named variant. Never send secrets, credentials, private user material, untracked files, or production payloads unless specifically authorized. Confirm resolved provider/model and report actual usage. If classification cannot run, report the blocker; do not quietly substitute regex.
- Establish a finite inventory and accountable dispositions; do not stop after a promising handful of results when the request covers the entire inventory. Continue batches autonomously until the stated scope is processed, a real blocker arises, or the user changes scope. Each batch saves progress and failures so it can resume.
- A classifier score, a static pattern, a mocked-boundary behavior, and a reproduced production incident are four different kinds of evidence. Never promote one to another. High scores are candidates; low scores are not proof of safety.

## Workflow

1. **Define the universe.** Pin revision and enumerate files, file types, generated code, tests, migrations and excluded material. Fetch all issues in the requested states/time window with pagination; deduplicate and compare declared counts. Save a private issue inventory. Classify each issue or explicitly mark it unclassified; group repeated symptoms and contracts rather than assuming shared root causes. Search existing open and closed issues before reporting a duplicate.
2. **Build a map.** Start with existing static-analysis tools and repository-specific tests. Use text search to seed candidates, then AST/type-aware queries, import/call graphs, entry points and cross-layer traces for ownership, error propagation and state transitions. Record parsed files, unresolved edges and dynamic-dispatch blind spots; graph coverage is not runtime coverage. See [discovery and coverage](references/discovery.md).
3. **Classify with controls.** If a model is authorized, send bounded source segments with stable IDs, prompt-injection-resistant instructions, relevant scope and tracked provenance. Use positive/negative controls and a pilot. Save per-segment scores, failures, model identity, exclusions, costs and retry state. Classify *every eligible segment* in the agreed denominator, including untagged files; split long segments safely or report them as uncovered. Validate schema and count results programmatically. Evaluate retrieval against known positives and negatives; report sampling/overlap bias, not fabricated precision or recall. See [classifier and measurement](references/classifier.md).
4. **Trace and challenge.** Prioritize potential data loss, destructive cleanup, ambiguous failure, retry/failover, incorrect success and cross-layer contract gaps. For each candidate follow callers, state ownership, durable writes, cancellation, UI and telemetry; compare sibling paths and existing issues. Look for protective behavior and intentional best-effort catches. Use [failure-boundary patterns](references/failure-boundaries.md).
5. **Prove the boundary.** Run the smallest deterministic local reproduction against the real relevant code, injecting failures at safe boundaries. Verify outputs, state and cleanup, and distinguish characterization of existing behavior from a failing regression. A mock-induced race proves the interleaving at that seam, not reachability in production. If a full environment or historical input is unavailable, investigate further where practical and state the gap. Preserve test commands and accessible sanitized evidence.
6. **Deliver and govern.** Independently check high-impact results and search for duplicates. Publish only when authorized, in the repository's issue format. For each issue identify symptom, exact code and revision, measured/reproduced evidence, conditions, unknowns, intended outcome, and a proportional verification. Group genuinely shared root boundaries; avoid duplicate or speculative tickets. If requested, create a roadmap linking new and existing issues without implying approval to implement, merge or close. Read back each external write.
7. **Report honestly.** Give user-facing findings and links first; summarize concrete scope, scanned/eligible/excluded/unresolved counts, validated findings, known false positives/negatives, costs and blockers. Explain whether work is still running. Finish only when the requested inventory and each candidate's disposition are accounted for, or identify the exact blocker and remaining work. Never equate a completed scan with a complete audit of all possible bugs.
